# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Go (module `telegram-business-bot`, Go 1.24+) Telegram business bot: a user bot, an optional separate admin bot, extra DB-configured "business bots", a USDT TRC20 wallet ledger, referrals, support tickets, message push campaigns, merchants, and a Gin web admin. MariaDB stores the data (GORM, AutoMigrate on startup) and Redis stores sessions and locks. User-facing text and docs are mostly Chinese.

## Commands

```bash
make test                      # go test ./...
go test ./internal/push -run TestName -v   # single test
make build                     # bin/xunzhou
make linux ARCH=arm64          # static cross-compile (CGO_ENABLED=0)
make dev                       # sources .env, then go run ./cmd/bot
docker compose up -d mariadb redis   # infra only, for local `make dev`
make up / make down / make logs      # full stack via Docker Compose
node --test internal/admin/ui_test.js   # admin UI JS tests (no browser needed)
TEST_MYSQL_DSN='user:pw@tcp(host:3306)/' go test ./integration/...  # real-DB financial tests
make test-integration                # same, in a throwaway MariaDB container
make e2e                             # whole app + fake Telegram + headless browser (e2e/run.sh)
```

The integration suite is skipped unless `TEST_MYSQL_DSN` is set. The DSN must **omit the database name**: the suite creates and drops its own uniquely named database and never reads `.env`.

## Architecture

- **Wiring**: `cmd/bot/main.go` → `internal/app/app.go` builds every service and starts the HTTP server (`/healthz`, `/telegram/webhook`, `/telegram/admin/webhook`, `/admin/*`, `/uploads`; the H5 shop; with split listeners (`API_HTTP_ADDR` + `OPERATOR_`/`MERCHANT_`/`SHOP_HTTP_ADDR`, see `App.Listeners`) the main one keeps only webhooks, uploads and `/uploads`, pages call the API cross-origin (`internal/cors`, `api-base` meta tag), console sessions are bound to the console origin, and uploads use one-time tokens), the background workers (push, business bots, TRON watcher), and the Telegram loops (polling or webhook, set by `TELEGRAM_MODE`).
- **One `telegram.Router`, several bots**: the same router type serves the user bot, the admin bot (`adminOnly=true`; only `ADMIN_IDS`), and each business bot (`.WithBotID(id)`). Each one gets its own Redis session namespace (`sessions.WithNamespace(...)`). Business bots are created in `internal/business`: tokens are stored AES-GCM encrypted (key from `BUSINESS_BOT_KEY`, or the primary bot token if that is empty) and each bot is polled under a lease.
- **`internal/lease`**: a Redis SETNX lease with renewal. It serializes per-user update handling (`tg:lock:...`), per-campaign push work, and business-bot polling across replicas. If ownership is lost, the work's context is cancelled. Use it for any new work that must not run concurrently.
- **Update error semantics**: if `Router.Handle` returns an error, polling rewinds its offset and a webhook returns 503, so Telegram redelivers the update. Return errors only for failures where a retry is safe. In webhook mode `keepWebhook` (`internal/app/webhook.go`) retries `setWebhook` with backoff and re-registers it if `getWebhookInfo` shows it removed or changed (every 10 minutes); Telegram or DNS/CDN failures never stop the program. Polling backs off (1s doubling to 30s) after a failed update, runs under a lease (`bot:poll:<kind>`, one instance per bot), and a panic while handling an update is logged and the update skipped. `/healthz` answers 503 when MariaDB or Redis is down. Client IPs use only `X-Forwarded-For` and only from `TRUSTED_PROXIES` (default: nobody; `private` = loopback/private networks); per-user update locks use a 20s lease (`lease.RunFor`); business pollers back off in place; news deliveries are retried only when nothing went out (429/5xx/no connection) and fall back from copy → photo → text only on content errors; RSS feeds cannot reach loopback/private addresses unless `NEWS_ALLOW_PRIVATE_FEEDS=1` (tests).
- **Wallet ledger** (`internal/wallet`): balances are split into available and frozen. Withdrawal flow: `available→frozen→pending→approved→completed` (completion deducts frozen; rejection returns frozen to available). `deposit_addresses` hold one address per user and network: `TRC20` (scanned by `trongrid.Watcher`) or `ERC20` (only shown to the user, with a QR code (`internal/qrcode`), in the bot and the shop; credited from the console). The console only assigns operator-owned addresses from `deposit_pool_addresses` (page 地址池), to one user or randomly to all users (replacing theirs); one address may serve several users (the address index is not unique; `store.New` drops the old unique one). Deposits are deduplicated per transfer (`deposit_orders.event_key`, `wallet.TRC20EventKey`; `tx_id` is not unique since one transaction may carry several transfers). The watcher (one instance at a time, lease `tron:watch`) credits an address directly only when it has had exactly one holder ever (`deposit_address_holders`, written by `setUserAddress`) and the transfer came after that holder got it; deposits to shared, re-assigned or no longer held addresses are recorded as `unclaimed`. A TRC20 claim is confirmed only against the watcher's record (none yet → refused), and the watcher credits through `CreditToHolder`, which re-checks under the lock that the address still has a single holder. Every path that credits a transfer first locks that transaction's records (`lockTransfer`, a `SELECT … FOR UPDATE` on `idx_deposit_orders_txid`; assign/confirm look up the tx outside the transaction first), so the watcher, confirms and assignments are serialised. Every other deposit is claimed by transaction hash and confirmed by people (a hash is public): `wallet.SubmitClaim` (bot `dep:claim`, H5 `POST /shop/api/wallet/deposit/claim`; ERC20 claims carry an amount, TRC20 ones take it from the watcher's record) records a per-user `pending` claim (`event_key` `claim:<network>:<hash>:<user>`, so several users may claim one hash), and the console confirms it with the verified amount (`ConfirmDeposit`; when the watcher saw the transfer the claim must be for that address and amount, and the record becomes `merged`) or rejects it, or assigns an unclaimed record to a user who holds or held the address (`AssignDeposit`); review data at `GET /admin/api/deposits/:id/review`. A transfer is credited once across all paths: TRC20 claims are confirmed only against an unclaimed watcher record with the same amount at an address the claimant holds or held (none yet → refused), which then becomes `merged`; the watcher credits through `CreditToHolder`, re-checking single ownership under the lock; ERC20 allows one credit per tx (`alreadyCredited`). These record `reviewed_by` and need the `funds` permission (as do balance adjustments, which take a request ID). A newly assigned address is scanned from the assignment on; an address no user holds any more stays watched (`deposit_pool_addresses.scan_timestamp`) and its deposits wait unclaimed. All credit paths call the deposit hook (notice + idempotent referral commission). Users are told about credited deposits (`wallet.WithDepositHook`, console credits) and withdrawal reviews through `business.NotifyUser` (the bot recorded on the withdrawal, `bot_id`, then any bot that reaches them); people see records as `wallet.OrderNo` (W/D/A + date + ID). Deposits from `trongrid.Watcher` are idempotent by `tx_id` and credit referral commission (`REFERRAL_RATE`) to the direct upline. The bot intentionally never holds TRON private keys or signs transactions; on-chain payout belongs in a separate signer.
- **Currencies** (`internal/wallet/currency.go`): `wallet_currencies` (seeded from `store.DefaultCurrencies`: `USDT` = TRC20, the shop and deposit currency; `USDT_ERC20`, `CNY`, `THB`, `MMK`, `USD`) gives each user one `wallet_accounts` row per currency. `Rate` is units per 1 USDT; `Exchange` (H5 `#/exchange`, `POST /shop/api/exchange`) converts at `to/from × (1 − exchange_fee_rate)`, refuses the request when the rates the user saw have changed, locks both accounts in one statement and is idempotent per request ID. Non-TRC20 money arrives via the console (`AdminAdjust`); `CreateCurrencyWithdrawal` freezes withdrawals of any withdrawable currency (network `ERC20` or `BANK`). Every currency's minimum and fee (fixed `withdraw_fee` plus `withdraw_fee_rate` × amount, rounded up, `wallet.WithdrawalFee`), USDT-TRC20 included, are set in the console (币种汇率); `WITHDRAW_MIN_USDT` / `WITHDRAW_FEE_USDT` only seed the USDT row once (`SeedWithdrawRule`). `Transfer` (`wallet/transfer.go`, `wallet_transfers`) moves one currency between users (recipient by @username or Telegram ID, no fee, idempotent per request ID); it creates both accounts before its transaction and then locks them in one ordered statement before any read, since an insert inside it deadlocks opposite transfers. The H5 我的 page has 充值 / 提现 / 转账 / 发红包 (`shop/wallethttp.go`, `/shop/api/wallet/*`, `/shop/api/redpackets`); spends need `X-Pay-Password`, and a packet made there belongs to the bot the shop was opened from, whose private chat gets the card with the inline share button (`telegram.SharePacketToSender`).
- **Red packets** (`internal/redpacket`, bot side `internal/telegram/redpacket.go`): types lucky / equal / exclusive / password in any wallet currency. Created in a wizard: in a private chat (menu `redpacket`, `/hb`), or right in a group (`/start` there, `/hb` still works; `/start <payload>` from a startgroup link only introduces the bot: one bot message edited step by step, answers are replies to it, only its starter may press its buttons, and it becomes the packet card); shares are fixed at creation (`Shares` JSON) and claimed in order under a row lock, one per user (`uk_packet_user`). The bot posts the card in the group or the sender shares it via inline mode (`@bot hb <code>`, `inline_query` is in `allowedUpdates`); the `hb:<code>` button claims, password packets are claimed by sending the password in their group (this needs privacy mode off) or, after pressing the button, in the private chat (5 wrong tries per packet per hour); a password typed in the private chat is never matched against other packets. `Service.Run` refunds expired packets (`redpacket_expire_hours`). Cards show the claim button only while the packet is open; `RefreshPacketMessages` redraws the group card and every inline copy seen so far (`red_packet_messages`) when a packet finishes or expires. A business bot with `purpose = redpacket` (`Router.WithRedPacketOnly`) offers only red packets, the wallet and the shop's exchange page; changing a bot's token or purpose restarts its poller. Console covers (`red_packet_covers`, page `redpacket_covers`) are offered after the greeting; a packet keeps the cover URL it was created with (`Cover`) and the Telegram file ID once sent (`CoverFileID`, reused for later copies and inline photo results), its card is then a photo whose caption is edited (`EditMessageCaption`, falling back to text edits) and lists fewer claims to stay under 1024 characters.
- **News** (`internal/news`, bot side `internal/telegram/news.go`): business bots with `purpose = news` (`Router.WithNewsOnly`) let users browse, search and subscribe per category (`news_subscriptions`, category 0 = all). Articles come from the console, RSS/Atom feeds (`FetchFeed`; the first fetch only archives) or source channels (`channel_post` → `IngestChannelPost`); groups/channels are recorded from `my_chat_member` into `news_chats`, where the console enables pushing or sourcing. `Service.Tick` (scheduled publishing, due feeds, `Fanout` into `news_deliveries` once per article) and `telegram.RunNewsDelivery` each run under a Redis lease; channel posts are delivered with `copyMessage` by the bot that reads the channel.
- **Payment password** (`internal/paypass`, bot side `internal/telegram/paypass.go`): six digits (no repeats/sequences), bcrypt; five wrong attempts lock it for 30 minutes (the counter is committed even when verification fails); the console resets it (`POST /admin/api/users/:id/paypass`). Every wallet spend asks for it: the bot's red packet and withdrawal wizards switch their session to `pay_*` steps in the private chat (a group wizard's confirm button is a t.me link to `/start hbpay_<request ID>`, since a callback answered with a URL opens a browser on some clients; password messages are deleted), and the shop sends `X-Pay-Password` with orders and exchanges (`checkPayPassword`), setting a first password via `POST /shop/api/pay-password`.
- **Dynamic menus** (`internal/menu`): read from `menu_items` on every render (`builtin` / `url` / `submenu` action types), so menu changes need no restart. Default rows are seeded in `store.seedDefaults`.
- **Push** (`internal/push`): `push_campaigns` are expanded into `push_recipients` and sent with rate limiting and retries. Supports scheduled, recurring, pause/resume/cancel/retry, and per-category bot routing through `business.Resolve`.
- **Web admin** (`internal/admin`): Gin JSON API plus single-file `index.html` / `login.html` embedded via `go:embed`. All frontend JS is inline in `index.html`, and `ui_test.js` loads it into a `vm` sandbox. Accounts live in `admin_users` (roles `super`/`admin`; `.env` credentials only bootstrap the first super admin). A Redis session stores `id:sha256(password_hash)`, so a password change, disable or delete revokes it; use `operator(c)` for the acting account. Non-super accounts get page permissions from their `admin_roles` template (`permissionKeys` in `internal/admin/roles.go`); every API route in `Register` is wrapped with `can(<page keys>)`, so a new route must declare its page, and account/role routes use `requireSuper`. The home page (`home`, `GET /admin/api/overview?range=today|7d|30d|all`, `overview.go`) holds the to-do counts and platform/per-currency statistics (no per-page stat cards); `store.New` grants `home` once to roles that had deposits or withdrawals. Navigation groups collapse (remembered in `localStorage`).
- **H5 shop** (`internal/shop`): a Telegram Mini App served at `/shop/` (single file `web/index.html`, API under `/shop/api/*`) and opened by the menu button when `SHOP_H5_URL` is set. Requests carry `X-Telegram-Init-Data`, verified against the primary and every enabled business bot token (`business.Tokens`), and map to the same `telegram_users` row and wallet. Products belong to existing `merchants`; orders cover one merchant and one delivery type (express / pickup / virtual) and are paid on creation via `wallet.Spend` inside the order transaction (`wallet.Refund` on cancel). Stock is decremented with a conditional `UPDATE ... stock >= ?`; order creation is idempotent per `(user_id, request_id)` and a multi-merchant checkout (`CheckoutRequest.Groups`) creates every order in one transaction with request IDs `<id>#<n>`. After-sales (`aftersale.go`) refund partially into the wallet and track `refunded_amount`; `Service.Run` auto-completes shipped orders. Console accounts with role `merchant` are limited to their `merchant_id` via `merchantScope(c)` / `shop.Scope` on every shop admin route; `platformOnly` guards shared shop data. Promo prices are never stored as the current price: `effectivePrice` applies a SKU's `promo_price` only inside the product's promo window, and `lines()` / `cards()` / `Product()` all go through it. Completing an order calls `recordSale` (ledger entry keyed `sale:<order>`); refunds after completion call `recordRefund`; settlements lock and claim the unsettled entries of final orders only (`commission_done`, i.e. past the after-sale period, which then closes), so a paid-out sale cannot be refunded; `MerchantBalance.SettleableNet` is that part. Platform discounts (platform coupons with `merchant_id = 0`, member tiers, points) are borne by the merchant by default; with system config `shop_discount_bearer = platform` the order stores them as `platform_subsidy` at creation and `saleBasis` settles the merchant on payment + subsidy (refunds take back the same share). A merchant's own coupon is always the merchant's. `ExpireGroups` also refunds `grouping` orders of already failed groups. Orders may carry `expected_pay` (the previewed total) and are refused if the total changed. Merchant accounts cannot set `featured` or `sales`; a buyer cannot cancel an order of a filled group.
- **Shop v4**: `CreateOrders` locks the buyer's `telegram_users` row as its *first* statement (REPEATABLE READ: a plain read before the lock would fix a stale snapshot) so per-user limits (`limit_per_user`) hold; promo stock (`promo_stock`, nil = unlimited) is decremented conditionally and a sell-out is an error, never a silent price change. `Service.Run` also calls `GrantCommissions`, paying `shop_referral_rate` to the buyer's referrer once an order is completed and past `shop_aftersale_days` (`commission_done` makes it once-only). Share links are `/start p<productID>_<referralCode>` (parsed in the router); notifications and `/orders` use `telegram.ShopButton` web_app buttons.
- **Shop v5**: member points/tiers live in `member.go` (`shop_members`, `shop_points_logs`; tier and points discounts are computed after the coupon in `orderDiscounts`, and spending points locks the member row). Member spend and points are granted when an order completes (`grantMemberTx`, from `recordSale`; `member_granted`/`member_spent`/`points_earned` on the order) and taken back proportionally by after-sale refunds after completion (`revokeMemberTx`); `GrantCommissions` catches up older completed orders and pays referral commissions after the after-sale period. Group buying (`group.go`): group orders start in status `grouping` (not fulfillable), `joinGroup` locks the `shop_groups` row, the order that fills the group flips all of them to `paid`, and `ExpireGroups` (in `Service.Run`, every 2 minutes) cancels and refunds the rest. Admin logins are throttled via `internal/ratelimit` (Redis fixed windows), H5 API calls per buyer too.
- **End-to-end checks**: `TELEGRAM_API_URL` lets the program talk to a fake Bot API server, so the whole app can run locally against temporary MariaDB/Redis and be driven with a headless browser (the H5 page needs `window.Telegram.WebApp.initData` signed with the bot token).
- **Shop v6**: buyer↔merchant messages (`message.go`, one `shop_conversations` row per buyer and merchant, unread counters on both sides) and merchant applications (`apply.go`; approval lives in `internal/admin/applications.go` because it creates the console account). `e2e/e2e.js` is the end-to-end script: extend it when adding user-facing flows; it fails on any page error, console error or HTTP ≥ 400. CI is `.github/workflows/ci.yml`.
- **Shop v7**: product CSV import/export (`importexport.go`) validates every product with `validateProduct` before writing, then saves all of them through `saveProductTx` in one transaction. Merchant payouts (`RequestPayout`, `createSettlementTx`) reuse the settlement ledger. Every console write, failed request and login goes through `Handler.audit` into `admin_audit_logs` (tests set `auditSink`); `PurgeAuditLogs` keeps 180 days.
- **Shop v8**: `merchant_staff` accounts share their owner's `merchant_id` (so `merchantScope` applies) with `permissions` limited to `merchantPermissions`; `merchantOnly` routes (payouts, staff management) are owner-only and `platformOnly` refuses both roles. The daily digest (`digest.go`) runs from `Service.Run` once per day per Redis date key. `internal/backup` dumps the DB in Go (consistent snapshot; date/time columns are read with `CAST(... AS CHAR)` because `parseTime` would otherwise produce RFC 3339 values MySQL rejects on restore); `integration/v8_test.go` restores a dump into a fresh database and compares it.
- **Shop home**: `Service.Directory` (`directory.go`, `GET /shop/api/directory`) mirrors the bot menus for ordinary users (enabled, non-admin top-level `submenu` items → nested `merchants` categories → enabled merchants); the H5 home renders a tab per top-level item and `#/merchant/:id` shows one merchant with its products. The system config `shop_categories_from_menu` (default 1, `Service.CategoriesFromMenu`, returned as `categories_from_menu` by `GET /shop/api/home`) picks the source: on, the home tabs and the console's 商城分类 page (read-only, `GET /admin/api/shop-categories/mode` → `MenuCategories`) follow the menus and a product's category shown in the console is its merchant's menu category (the form keeps any hand-kept `category_id`, 0 allowed); off, both use the hand-kept `shop_categories` and each tab lists its products.
- **Duplicate inserts**: do not use `OnConflict{DoNothing}` + `RowsAffected` to detect duplicates on tables with an auto-increment ID: on MariaDB GORM appends `RETURNING id`, so a skipped row still reports 1. Insert normally and check `store.IsDuplicate(err)`. Money-path tests live in `integration/shop_test.go` and need `TEST_MYSQL_DSN`.
- **Schema changes**: add the model in `internal/model/models.go` and register it in the `AutoMigrate` list in `internal/store/store.go`.

## Testing conventions

Service unit tests use `internal/testutil.DB(t, steps...)`, a scripted fake SQL driver. Each `Step` must match the next query in order (`Contains` substring, optional `Args`), and any unexecuted steps fail the test. When you change a service's queries, update the step scripts to match. Redis-dependent code takes small interfaces (e.g. `lease.Client`) so tests can fake it.

`internal/app/app_media_integration.go.txt` is a patch note, not compiled code.
